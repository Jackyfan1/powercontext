# 周边去哪儿：基于高德的地点推荐助手

## 1. 技能用途

把用户的一句自然语言出行需求，变成一份可信的周边地点推荐清单：

- 输入：城市、起点（评测会给出明确起点坐标，形如 `120.153576,30.287459`，即“经度,纬度”）、自然语言需求（地点类型、步行时间上限、推荐数量、偏好）。
- 输出：最多 3 个从同一起点出发、可独立步行到达的地点，含名称、地址、步行距离、步行时间、推荐理由。
- 原则：所有地点与路线数据必须来自高德 MCP 的真实返回；缺依据的信息一律标注“未核实”，绝不编造。

## 2. 需求解析（写进心里，不必复述给用户）

从用户话里抽取以下要素，缺失的用默认值：

| 要素 | 说明 | 缺省处理 |
| --- | --- | --- |
| 城市 | 如“杭州”“北京” | 用起点坐标所在城市，不做猜测 |
| 起点 | 优先使用给出的经纬度 `经度,纬度` | 只给地名时，先用地理编码/关键词搜索换成坐标 |
| 地点类型 | 咖啡馆、餐厅、公园、便利店等 | 未指明时按“附近值得去的地点”处理 |
| 步行时间上限 | 如“步行不超过 15 分钟” | 不限时也要报步行时间 |
| 推荐数量 | 用户要求 N 个 | 默认 3，且**任何情况下最多 3 个** |
| 排序偏好 | “优先近一点”“评分高一点”等 | 默认按步行时间由近到远 |

抽取示例：“我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。”
→ 类型=咖啡馆，上限=15 分钟，数量≤3，排序=步行时间升序。

## 3. 可用工具（高德 MCP Server）

以运行时实际挂载的工具名为准，按工具描述选择语义匹配的工具。常见名称与用途：

| 用途 | 典型工具 | 关键参数 |
| --- | --- | --- |
| 周边搜索（首选） | `maps_around_search` | `keywords`、`location`（经度,纬度）、`radius`（米） |
| 关键词搜索（补充） | `maps_text_search` | `keywords`、`city` |
| 步行路线规划（必用） | `maps_direction_walking` | `origin`、`destination`（均为“经度,纬度”） |
| 地点详情（可选） | `maps_search_detail` | `id`（POI ID） |
| 地理编码（起点只给地名时用） | `maps_geo` | `address`、`city` |
| 逆地理编码（可选） | `maps_regeocode` | `location` |

要点：
- 只有“步行路线规划”返回的 `distance`（米）/`duration`（秒）才能用于回答中的步行距离与时间。
- 周边搜索返回的 `distance` 是到搜索中心的直线距离，**只能用于内部排序，不能写进回答**。
- 不要调用与任务无关的工具（天气、打车、驾车/公交路线、生成专属地图等）。

## 4. 执行流程

### 第 1 步：确认起点
起点坐标已给出时直接使用，不要重复地理编码。只有用户仅给地名、缺坐标时，才用地理编码/关键词搜索解析出 `经度,纬度`；解析失败就请用户补充更明确的起点，不要猜坐标。

### 第 2 步：周边搜索
- 检索半径按步行上限换算，步行速度按约 90 米/分钟估算，再留一点余量：
  `radius ≈ 步行时间上限(分钟) × 90`，并限制在 500–3000 米之间。
  （例：15 分钟 → 约 1350 米；未给时间上限 → 用 1000 米，最多放大到 2000 米。）
- 关键词用用户要的地点类型；太宽泛时加限定词（如“咖啡馆”“餐厅”）。
- 一次搜索通常返回多个候选；用户要的类型不明显时，可按同义词补一次搜索（如“咖啡”/“咖啡馆”），避免关键词过窄导致空结果。

### 第 3 步：候选筛选
从搜索结果中挑选候选，规则：
1. 类型匹配：以返回的名称、`type`、`typecode` 判断是否符合用户要的地点类型；明显不符的（如把便利店、奶茶店当咖啡馆）剔除。
2. 去重：同一品牌/同一地点重复出现时只保留一个。
3. 预排序：按返回的直线距离升序排列，仅用于决定先查哪些地点的步行路线。

### 第 4 步：步行路线核验（关键）
对预排序后的候选依次调用步行路线规划（起点为同一起点，终点为该地点坐标），逐个核验：
- 记录该次调用返回的步行 `distance` 与 `duration`。
- `duration` 超过用户步行时间上限的候选**直接淘汰**，不得列入推荐。
- 凑够 3 个合格地点即停止；为避免过度调用，最多核验 6 个候选。若全部核验完仍不足 3 个，按实际数量回答。
- 每个推荐地点都是一次独立的“起点→该地点”路线，不拼成多站行程。

### 第 5 步：排序
- 用户说“优先近一点/近的优先”→ 按步行时间升序（时间相同按距离升序）。
- 未提偏好 → 同样按步行时间升序，保证推荐顺序与路线数据一致，并在理由里点明“距离最近/步行最短”。

### 第 6 步：生成回答
按下文“回答格式”输出，只写有数据支撑的内容。

## 5. 回答格式

先给一句结论，再给表格，最后补简短说明：

```markdown
从「<起点名称或坐标>」出发，为你找到 N 个步行 ≤ <上限> 分钟的<地点类型>推荐（按步行时间由近到远）：

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | XX咖啡（XX店） | XX路XX号 | 约 450 米 | 约 6 分钟 | 本次结果中步行最短，约 6 分钟直达 |
| 2 | ... | ... | 约 1.1 公里 | 约 14 分钟 | 步行 14 分钟，仍在 15 分钟限制内 |

说明：以上距离与时间均来自步行路线规划结果；营业状态、排队情况、安静程度等未在高德数据中体现，均未核实。
```

书写规范：
- 距离：`<1000` 米用“约 N 米”，`≥1000` 米用“约 X.X 公里”（保留 1 位小数），取整不夸大可达性。
- 时间：由 `duration` 秒换算成分钟并向上取整（如 780 秒 → “约 13 分钟”），只能来自路线结果。
- 地址：用 POI 返回的 `address`；若为空或缺字段，写“高德未返回详细地址”，不要编造。
- 推荐理由：一句话，必须能对上数据（步行时长/距离/在同批候选中最近等）；不得虚构评分、环境、人气、营业时间。
- 数量：表格行数 = 实际合格地点数，最多 3 行；用户要求的数量更少时按用户数量。

## 6. 异常与边界处理

| 情况 | 处理方式 |
| --- | --- |
| 合格地点不足 3 个 | 有几家推几家，并说明“在步行 ≤ X 分钟的范围内只找到 N 家符合条件的<类型>”；可建议放宽步行时间或换地点类型，不点名列出超时地点 |
| 搜索无结果 | 先做一次合理放宽（换同义关键词或把半径扩大到上限），仍无结果则如实说明“该范围内未找到符合条件的<类型>”，建议放宽条件；不得编造地点 |
| 工具调用失败/超时 | 同一请求最多重试 1 次；仍失败则说明“高德服务暂时不可用，无法核实地点与路线”，不输出未经核实的地点 |
| 起点无法解析或缺坐标 | 请用户补充明确起点（地铁站/地标/地址），不要假设坐标 |
| 信息缺失（营业状态、排队、安静程度、评分等） | 一律标注“未核实”，或直接不写 |

## 7. 硬性约束（必须遵守）

1. 回答中的每个地点都必须来自本次高德搜索返回结果，名称、地址、坐标不得改写或虚构。
2. 回答中的步行距离与时间必须来自该地点的步行路线规划结果，禁止用直线距离、估算值或地图外知识替代。
3. 不得超过用户步行时间上限，不得把超时地点列为符合条件的推荐；推荐数量不超过 3 个。
4. 推荐顺序必须与步行路线数据一致（“优先近一点”时按步行时间升序）。
5. 不编造评分、营业时间、排队情况、环境安静程度等无数据支撑的信息；没有依据就写“未核实”或不写。
6. 不要在回答中输出高德 API Key、工具原始 JSON、内部推理过程或调用日志。
7. 回答使用用户提问的语言，简洁、可直接照着走。
